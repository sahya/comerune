## 順序依存が強い Issue

以下は**前の Issue が完了しないと着手できない**。

```
#32 → #33 → #34 → #35           (整形の段階的構築)
#39 → #40 → #41 → #42           (JNI基盤 → 人間準備 → C++実装 → Kotlinラッパー)
#43 → #44                        (再生 → Audio Focus)
全コンポーネント → #46 → #47 → #48   (統合→Plugin→Dart)
```

## クリティカルパス

最も長い依存チェーン:

```
#39 → #40(人間) → #41 → #42 → #46 → #47 → #48
```

**#40（人間作業 30分〜1時間）がゲート**。これを早めに消化すれば、残りは全て AI で並列進行できる。

## 実装セッション計画

Issue は1つずつ実装・テスト・レビューを回す。
ただし小さい Issue や対になる Issue はセッション内でまとめてよい。

| Session | Issue | まとめる理由 | 単独にすべき Issue と理由 |
|---|---|---|---|
| 1 | **#32** (データモデル) | — | 全 Issue の土台。先に確定させる |
| 2 | **#33 → #34 → #35 → #36** (整形系) | 全て純粋ロジック。同一クラスへの段階的追加 | #33→#34→#35 は直列依存。#36 は #33 の後なら可 |
| 3 | **#37 + #38 + #45** (キュー・設定・イベント) | 各30行程度の小さな実装。互いに依存なし | — |
| 4 | **#39** (JNI 基盤) | — | ビルド通過の確認を単独で行うべき |
| — | **#40** (人間作業) | — | 人間がヘッダ配置・設計判断。AI セッション外 |
| 5 | **#41** (C++ 本実装) | — | JNI は不具合が見えにくい。固定文字列で音が出る確認を挟む |
| 6 | **#42** (VoicevoxEngine) | — | #41 の動作確認が取れてから着手。障害箇所の切り分けのため |
| 7 | **#43 + #44** (WAV 再生 + Audio Focus) | 再生と Audio Focus は同じ MediaPlayer 上の責務 | — |
| 8 | **#46** (SpeechController) | — | 全コンポーネント統合点。非同期バグはここで出る。最も慎重に |
| 9 | **#47 + #48** (Plugin + Dart ラッパー) | Plugin と Dart は MethodChannel の両端。一緒の方が整合しやすい | — |

### まとめてよい根拠

- **Session 2 (#33-#36 整形系)**: 同一クラス (`DefaultCommentNormalizer`) へのルール追加。テストも同じテストクラスに蓄積される
- **Session 3 (#37+#38+#45)**: 各 Issue が 30 行程度と非常に小さく、互いに無関係。3つ合わせても1 Issue 分の規模
- **Session 7 (#43+#44)**: Audio Focus は MediaPlayer の付随機能。別にすると WavPlayer を2回触ることになる
- **Session 9 (#47+#48)**: MethodChannel の送信側と受信側。片方だけ作っても動作確認できない

### 単独にすべき根拠

- **Session 5 (#41)**: C++ / JNI のバグは Kotlin 側からは「null が返った」としか見えない。合成単体で確認を挟まないと原因不明になる
- **Session 6 (#42)**: Kotlin ラッパーと C++ 実装を同時に書くと障害箇所が2層にまたがり切り分けが困難
- **Session 8 (#46)**: 全依存を結合する箇所。非同期制御 (Mutex, CoroutineScope) のバグは統合時に初めて発覚する
