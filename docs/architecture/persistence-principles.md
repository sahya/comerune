# 永続化原則（AI エージェント・開発者向け）

## 目的

このドキュメントは、ユーザー属性（コメント色、コテハン等）の永続化レイヤーを将来変更する際に、**2 つの独立した失敗クラスへの防御**を誤って削除しないための設計原則をまとめたものです。

過去の永続化インシデントの調査を通じて確立された、以下の歴史的教訓を記録します:

- ユーザーに観測された症状の主要な根本原因は、ストレージバックエンド（キー・バリューストア）そのものではなかった
- 主要な根本原因は、**書き込みが開始される前に永続化がサイレントにスキップされていた**ことだった
- 書き込み完了制御のハードニングは依然として重要だが、それは**二次的な防御層**である

重要な区別:

1. **ユーザーに観測されたバグの最終的な根本原因は**:
   - 放送者の識別子が解決されなかった
   - 保存処理のガード条件（識別子が null 以外であることを要求）により、永続化呼び出し自体が実行されなかった

2. **書き込み完了制御が依然として重要な理由**:
   - 一度保存パスに入った後、ライフサイクル終了近くで未完了の書き込みが失われる可能性がある
   - 今後のバックエンド変更でこのクラスのバグを再導入するのは容易

---

## 2 つの独立した失敗クラス

永続化関連の変更では、以下の 2 つの失敗クラスを混同しないこと:

### クラス 1: 保存パスが一度も入らなかった

- 例: 放送者識別子が未解決で、保存処理のガード条件により早期 return された
- 症状: ユーザーが設定を変更しても、最初からディスクに書き込まれない
- 検出方法: 「保存をスキップしました」という警告ログ

### クラス 2: 保存パスには入ったが、完了が制御されなかった

- 例: fire-and-forget の書き込み、pending write の明示的 drain なし、完了前にアプリがキルされた
- 症状: 同一プロセス内では設定が残るが、アプリ終了後に消える
- 検出方法: 書き込み関数は呼ばれているが、ディスクに反映されていない

書き込み完了制御のハードニングはクラス 2 にのみ効果的であり、クラス 1 には効果がない。

---

## 歴史的根本原因

過去のインシデントの最終診断:

- 全ての接続エントリポイント（直接入力、手動接続、フォロー一覧、お気に入り、自分の放送）は、最終的に同じ放送者解決フローに収束していた
- 放送者 identity が解決されない場合、内部状態の放送者 ID が null のままだった
- ユーザー色 / コテハンの保存ハンドラは、放送者 ID が null 以外であることを要求していたため、早期 return していた

つまり元のユーザー向け失敗モードは:

- 「書き込みが開始されて flush されなかった」**ではなく**
- 「保存パスがサイレントにスキップされて書き込みが一度も開始されなかった」

この失敗は UI 上は接続経路ごとに異なって見えるが、全て同じ根本的失敗（放送者 ID 解決が永続化キーを得られない）を共有していた。

---

## 書き込み完了制御のハードニングモデル

書き込み完了制御のハードニングは、以下のリスクパターンに基づく:

- ユーザー色 / コテハンは同一アプリセッション内の再接続では残る
- ユーザー色 / コテハンはスワイプキル + 再起動後に消える

保存パスがアクティブであることが分かっている場合、この症状は強く示唆する:

- 同一プロセス寿命中はメモリ内状態は正しい
- ディスク永続化が弱い部分である
- 失敗モードは「読み取りロジック不良」ではなく「書き込みが開始されたが完了前にプロセスが死んだ」

主要リスク:

- fire-and-forget の永続化呼び出し
- ライフサイクル終了前の pending write の明示的 drain がない
- in-flight 書き込み完了の統一された所有権がない

---

## 保護すべき設計原則

バックエンドが変わっても保持すべき設計アイデア:

1. 永続化書き込みは**追跡**されるべきで、fire-and-forget してはならない
2. 同じ論理データセットを変更する書き込みは**直列化**されるべき
3. プロセス死亡に先行する可能性のあるライフサイクル遷移で、アプリは pending write を明示的に **drain** すべき
4. 呼び出し元が未完了の Future を放置できる限り、ストレージバックエンド単独では不十分である

これが意味すること:

- ストレージバックエンドを置き換えても自動的に保護は維持されない
- OS レベルのディスクフラッシュ（fsync 相当）だけでは書き込み追跡の代替にならない
- 「より耐久性のあるバックエンド」と「適切な書き込みライフサイクル管理」は別の関心事である

---

## 中核原則

ユーザー操作が永続状態を変更する場合、システムは次の問いに答えられなければならない:

> 「この書き込みの完了を表す正確な Future は何か、そしてアプリ終了前にそれを待つ責任は誰にあるのか？」

答えが「誰もいない」または「UI のどこかで fire-and-forget されている」なら、システムは依然として脆弱である。

---

## 誤解してはいけないこと

今後の変更では、書き込み完了制御を以下のように解釈してはならない:

- 「ストレージバックエンドが主要な根本原因である」
- 「バックエンドを変更するだけでバグが解決する」
- 「同期的ディスクフラッシュを行うバックエンドなら、ライフサイクル drain は不要」
- 「読み取り側のキャッシュ問題が主要な問題である」
- 「書き込み完了制御が元の主要根本原因修正である」

これらは別の関心事である。

---

## 非交渉制約

ユーザー属性の永続化を変更する場合、保存パスが実際に到達可能になった後は、以下のプロパティを保持すること:

### 1. Pending write draining

全ての in-flight 書き込みの完了を待つメカニズムが必要。

この契約は以下のようなライフサイクル出口に配線されたままでなければならない:

- 非アクティブ状態（`inactive`）
- 一時停止状態（`paused`）
- デタッチ状態（`detached`）

### 2. 同一論理データへの書き込みの直列化

複数の書き込みが同じ放送者のユーザー属性を対象とする場合、lost update を引き起こすような形でインターリーブしてはならない。

インデックスファイルのような共有メタデータがある場合、その共有メタデータにも独自の直列化戦略が必要。

### 3. バックエンド非依存の正しさ

アプリは以下のいずれの場合でも安全でなければならない:

- バックエンドがキー・バリューストア
- バックエンドが放送者単位のファイル
- バックエンドが将来また変わる

正しさ契約は、ストレージプリミティブレベルではなく、永続化ワークフローレベルに属する。

### 4. 失敗の可視性

書き込み失敗や破損を、明示的な復旧ポリシーなしにサイレントに「空データ」に変えてはならない。

最低限:

- 失敗を明確にログする
- リトライ・フォールバック・明示的エラー surfacing のいずれが適切かを判断する

---

## バックエンド移行後もこれが重要な理由

ユーザー属性が 1 つのストレージから別のストレージに移動しても、書き込み完了制御の哲学は依然として重要。各バックエンドには独自の失敗モードがある:

- キー・バリューストアでは、非同期ディスクフラッシュがプロセス死亡前に完了しない可能性がある
- ファイル永続化では、直接上書きが中断後に部分的／切り詰められた内容を残しうる
- より強いアトミック性のために、一時ファイル書き込み + rename が必要な場合がある
- 完了基準が厳格でないと、部分的に成功したままのマイグレーションが発生しうる
- アプリ終了が未完了の書き込み Future と競合しうる

正しいメンタルモデル:

- まず保存パスが実際に入ることを保証する
- バックエンド移行は耐久性を改善しうる
- 書き込み完了制御は保存開始後のセマンティクスを保護する
- 両方が必要かもしれないが、異なる失敗クラスを解決する

---

## 今後の変更時のレビュー質問

永続化関連の変更をレビューする際に問うべきこと:

1. 書き込み開始前に保存パスがスキップされる可能性があるか？
2. 書き込みを実行可能にする正確なキーまたは identity は何か？
3. 全ての in-flight 書き込みの完了を正確に追跡しているものは何か？
4. それらの書き込みを待つライフサイクルイベントは何か？
5. 同じ論理データへの 2 つの書き込みが互いを上書きする可能性があるか？
6. 共有メタデータの更新が互いに競合する可能性があるか？
7. 書き込み中にプロセスが死んだら何が起こるか？
8. マイグレーションが部分的に成功したら何が起こるか？
9. ストレージが破損している場合、アプリはサイレントにユーザーが「データを失った」ように見えるか？

## 安全な要約

書き込み完了制御の最も安全な短い要約:

> 書き込み完了制御のハードニングは、元の主要根本原因修正ではなく、保存パスが開始された後の完了を保証する二次防御層である。

過去のインシデント全体から学ぶべき結合要約:

- まず永続化がサイレントにスキップされるケースを修正する（クラス 1）
- 次に開始された書き込みが失われないように書き込みライフサイクル保護を維持する（クラス 2）

今後の作業がこの区別を維持すれば、バックエンド変更を安全に積み上げることができる。
今後の作業がこれらの関心事を 1 つに潰すと、将来のデバッグが非常に困難になる。
